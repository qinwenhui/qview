# qview 正则搜索测试指南

> 用 `tests/gen_regex_test.py` 生成一份**确定性**、富含可计数标记的日志，配合本指南列出的
> 正则模式组，逐条在 qview 里验证正则搜索结果是否与期望命中数一致。脚本会打印（并写入
> `.expected.txt`）每种模式的期望命中数，qview 会报告**精确的总命中数**，两边对上即通过。

---

## 1. 快速开始

```bash
# 生成 100 万行（约 141 MB）默认输出 regex_test.log，并打印期望命中对照表
python tests/gen_regex_test.py

# 小文件快速验证（期望数等比例缩放，但请以脚本输出为准）
python tests/gen_regex_test.py --lines 100000 --out small.log

# 超大文件跳过计数（只生成数据）
python tests/gen_regex_test.py --lines 10000000 --no-count
```

在 qview（egui GUI）中：

1. 打开生成的 `regex_test.log`；
2. 工具栏点击 **`.*`** 开启正则搜索（按钮变蓝），**Aa** 保持默认关闭；
3. 输入下表的正则，回车；
4. 对比**状态栏显示的总命中数**与表内"期望命中"（或脚本打印的数值）。

> 数据生成用固定种子（`SEED=20260805`），任何机器重复生成字节完全一致；期望命中数因此是
> **精确**的（不是近似），可放心对账。

## 2. 测试数据说明

每行格式（80–200 字节，字段均可作正则目标）：

```
[2026-01-01 00:00:00.000] [INFO] [api] worker-11 req=e952ebc10aa4f028 ip=192.168.234.152 dur=609us status=301 "request processed" seq=0000000000
```

| 字段 | 取值 | 适合测什么 |
|---|---|---|
| 时间戳 | 2026-01-01 起，每行 +250ms（1M 行 ≈ 2.9 天） | 日期/时间正则 |
| `[级别]` | INFO 60% / WARN 20% / ERROR 15% / DEBUG 5% | 大小写、词边界 |
| `[服务]` | auth / api / db / cache / gateway / job（均匀） | 交替、词边界 |
| `worker-NN` | 01–32，两位补零 | 字符类、量词 |
| `req=` | 16 位小写十六进制 | hex 字符类、`{n}` |
| `ip=` | 192.168.a.b（a 0–255，b 1–254） | IP 正则 |
| `dur=` | 1–9999us | 量词范围 |
| `status=` | 2xx 50% / 4xx 30% / 5xx 20% | 字符类、交替 |
| `"消息"` | 内嵌可计数标记 | 见下 |

消息里内置的**可计数标记**（按比例出现，便于对账）：

- `TIMEOUT`（独立词）vs `TIMEOUTRETRY`（前缀词）→ 测 `\bTIMEOUT\b` 边界
- `ERROR`（独立）vs `ERRORS`（前缀）vs `ERROR-CODE-404` / `ERROR-500` / `ERROR-503`
  （带连字符）→ 测 `\bERROR\b`、`\bERROR`、`ERROR` 的区别
- 少量中文消息（`用户登录成功` / `磁盘空间不足`）→ 测 `\p{Han}` Unicode
- 刻意**不含**小写 "error"/"timeout" → Aa 开关（大小写）不影响大多数模式的命中数

## 4. qview 正则语义要点（务必阅读）

qview 用 `regex::bytes::Regex`（`regex` crate 1.10+）在**原始字节**上匹配。以下行为都是实测
验证过的：

### 4.1 大小写：Aa 默认关闭 → 模式自动包 `(?i)`

Aa 关（默认）时 qview 把输入拼成 `(?i)<模式>`。所以 `error` 能命中 `ERROR`。开启 Aa 后按原样
编译。由于数据不含小写 "error"/"timeout"，表中大部分模式的命中数**不受 Aa 影响**；刻意
测大小写时用 3.7 的例子。

### 4.2 行锚点必须写 `(?m)`

qview 在流式窗口上匹配，**不开 `(?m)` 时 `^`/`$` 是按缓冲区（窗口/分块）边界锚定**，不是行。
写 `(?m)^` / `(?m)$` 才能按行。表中的行锚点全部带 `(?m)`。

### 4.3 `.` 不跨行，且在 bytes 模式下按"字节"计数

- `.` 匹配除 `\n` 外的任意**字节**：中文 1 字 = 3 字节 = 3 个 `.`（测 `\p{Han}` 而不是 `.`）。
- 正则不会匹配跨行内容（`.`, `\w+` 等都不会吞 `\n`）。

### 4.4 不支持环视与反向引用

`regex` crate **不支持** lookahead/lookbehind（`(?=…)`、`(?<=…)`）与反向引用（`\1`）。
输入这类模式会编译失败，qview 提示正则无效——这不是 bug。

### 4.5 线性时间（不会卡死）

`regex` crate 是自动机实现，**不存在灾难性回溯**。像 `([0-9]+)+`、`(a|aa)+` 这类在 PCRE /
Python `re` 上可能指数级回溯的模式，在这里都是线性时间。可以放心输入来测（见 3.9）。

### 4.6 Unicode 类默认开启

`\d`/`\w`/`\s` 默认是 Unicode 感知的（匹配各种文字的数字/字母/空白）；`\p{Han}` 等
Unicode 脚本属性可用。数据全 ASCII 时 `\d` 与 `[0-9]` 等价。

### 4.7 `^` 锚点分块边界伪命中（已修复）

并行扫描把文件切成任意字节的分块，**每块段首原本被当作 `^` 的匹配位置**：若分块边界恰好落在
非行首的 `[`（如级别/服务标签 `[WARN]`、`[db]`），`(?m)^\[` 会多计一个伪命中（实测出现过 +1）。

**已修复**：分块扫描现在**对齐到真实行首**——每块向前回看上一个 `\n`（`memrchr`，上限 64KiB，
与扫描器的回看窗口一致），把扫描起点放在行首，让 `^`/连串模式看到真实上下文；对齐前缀里的
命中由前一块计数、本块跳过。修复后 `(?m)^\[`、`(?m)^\[20\d{2}` 等与脚本期望完全一致。

**遗留限制**：单行超过 64KiB（MAX_LINE/MAX_LEAD）的病态文件里，回看找不到上一个 `\n` 的
分块可能仍偶发 ±1（每块最多 1 个），与命中总数相比可忽略。

### 4.8 连串模式（`\S+` / `\d+` 等）分块边界多计（已修复）

同源问题：`\S+` / `\d+` / `\w+` / `[a-z]+` / `([0-9]+)+` 等连串模式的起点可在任意字符，跨分块
边界的连串会被前后两块各计一次（实测 `\S+` +29、`\d+` +11）。

**已修复**：同上——扫描对齐到行首后，引擎看到连串的真实起点，跨边界的连串只计一次。修复后
`\S+`、`\d+` 与脚本期望完全一致；单字符（`\d`、`\.`、`-`）与带字面量前缀（`dur=`、`status=`、
`req=`、`ERROR-`）的模式本来就没问题。

### 4.9 CRLF 文件的 `$` 锚点已自动处理

qview 读原始字节，`(?m)$` 匹配 `\n` 前的位置；CRLF 文件里数字与 `\n` 之间隔着 `\r`，裸 `$`
本来**完全搜不到**（实测 0）。已修复：打开文件时检测行尾（`Engine::uses_crlf()`，抽样首 64KiB），
若为 CRLF 就把正则的 `$` 锚点自动改写为 `(?:\r?$)`（`\$` 字面量与 `[...]` 内的 `$` 不动），
使 `(?m)seq=\d+$` 在 CRLF 上也能命中每行。这与既有"多行字面量查询按行尾归一化"一致。
仍按原始字节的：`.`、`[^\n]` 会把 `\r` 当作普通字符匹配。

### 4.10 整词（`\b` 按钮）在正则模式下被忽略

工具栏的 `\b`（整词匹配）只作用于**字面量**搜索。开启 `.*` 正则后，qview 走正则分支，
`whole_word` 不生效——想整词就自己写 `\b…\b`。

### 4.11 TUI 暂不支持正则

`qview`（TUI）搜索走默认 `SearchOptions`，只做字面量。正则搜索目前是 egui GUI 的功能
（工具栏 `.*`）。

### 4.12 编码（UTF-8 / GBK / Shift_JIS …）与字节级搜索

搜索在**原始字节**上执行（`regex::bytes` / memmem），不感知编码：

- `\n`(0x0A) 切行对 UTF-8、GBK、GB18030、Big5、Shift_JIS 等**都安全**（0x0A 永不是这些编码的
  尾/续字节）→ 上面的分块对齐与行模型不受编码影响。
- `\p{Han}`、`\d` 等 Unicode 类按 **UTF-8 字节**匹配（汉字 = 3 字节，`.` 逐字节）；仅对 UTF-8
  文件有效。
- **非 UTF-8 文件**（如 GBK）：非 ASCII 字面量/类无法用 UTF-8 输入命中——这是字节级搜索的固有
  限制（`encoding` 设置只影响**显示**解码，不改变搜索字节）。测中文请用 UTF-8 文件（本生成器
  输出即 UTF-8，含少量中文消息，见 3.8）。
- 特殊字符：`$`/`\r` 等按字面字节处理（CRLF 见 4.9）。

### 4.10 整词（`\b` 按钮）在正则模式下被忽略

工具栏的 `\b`（整词匹配）只作用于**字面量**搜索。开启 `.*` 正则后，qview 走正则分支，
`whole_word` 不生效——想整词就自己写 `\b…\b`。

### 4.11 TUI 暂不支持正则

`qview`（TUI）搜索走默认 `SearchOptions`，只做字面量。正则搜索目前是 egui GUI 的功能
（工具栏 `.*`）。

## 5. 性能观察（顺带）

用这份 1M 行数据还能顺便测性能与内存设计：

- `\d`（约 5,750 万命中）：验证**超大结果集的精确总数**——总数永远精确，但命中位置
  超出 `max_samples` 采样上限时走"隔段采样"，导航到未采样区间会回退重扫（这是设计，不是丢结果）。
- `(?m)^\[` 这类高频模式整文件单遍扫描应在毫秒级；可对比不同 `--window`/线程下的耗时。
- 进程内存与文件大小无关（流式 NO_BUFFERING 扫描），任务管理器观察即可。

## 6. 口径与对账

- 脚本的期望值 = 按 **Aa 关（`(?i)`）逐行（含换行符）**统计，与 qview 默认行为一致。
- 对表内**所有**模式（含 `^` 锚点与 `\S+`/`\d+` 连串），脚本值 == qview 全文件精确总数
  （已用真实引擎逐条核对；分块边界对齐修复见 §4.7/§4.8，回归测试在
  `core/tests/regex_boundary.rs`）。
- CRLF 文件：GUI 自动按文件行尾处理 `$`（§4.9），期望值按实际行尾对账。
- 期望值写入 `<out>.expected.txt`，可留存用于跨版本回归。
- 想自动化：仿照 `qview-bench`，把上表模式喂给 `qview_core::search::run_search` 断言
  `total_count()`。
